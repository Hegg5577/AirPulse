## 新版官方驱动证据

来源：<https://drive.nuphy.io/static/js/main.eff2c3e9.js>。
使用 TypeScript 语法树提取模块，只在隔离 VM 中运行字符串解码函数，不执行驱动模块或访问 USB。

模块 `40877`：

| 命令 | 编号 | 用途 |
| --- | --- | --- |
| GetLightState | `0xD5` | 读取灯光状态 |
| SetLightState | `0xD6` | 写入灯光状态 |
| GetKeyLightColor | `0xD2` | 读取灯珠颜色 |
| SetSignalColor | `0xD8` | 逐灯珠写入颜色 |

模块 `86736` 的机械适配器现在覆盖了 `setCustomLight`：

1. 使用 `lightMapping.ledIndexByKeyPosition` 将键位映射为灯珠索引。
2. 每项编码为 `[灯珠索引, R, G, B]`。
3. 使用 `SetSignalColor`、地址 0、当前模式 handle 提交数据。

旧记录中“机械适配器未覆盖 setCustomLight”的结论仅适用于旧版官方脚本，不能继续用于新版。虽然旧探针曾猜测使用 D8，其键位映射、分包、模式选择和恢复仍未验证，不能因此直接启用。

同模块 `getLightStates` 在 `97822.PY(keyboardType, firmwareVersion)` 成立时读 22 字节，否则读 17 字节。该判断对应功能 `presetShapeLightMode`，当前尚未解出 Air75 V3 的具体版本门槛。

新增字段布局：

| 偏移 | 字段 |
| --- | --- |
| 0–8 | 原主键区字段 |

## 本轮主键区复测

运行现有 `--diagnose-main-brightness`，Windows 模式 handle 1。用户通过每一步系统弹窗确认实体效果。

| 目标亮度 | 实际回读 RGB | 人工观察 | 侧灯 |
| --- | --- | --- | --- |
| 100% | `00 00 FF` | 稳定蓝色，确认通过 | 不变 |
| 10% | `00 00 1A` | 相比 100% 明显变暗，确认通过 | 不变 |
| 60% | `00 00 99` | 相比 10% 明显变亮，确认通过 | 不变 |
| 0% | `00 00 99` | 主键区全部熄灭，确认通过 | 不变 |

初始主键区为 `04 64 03 00 00 00 F6 00 FF`。诊断与共用函数恢复均返回成功，用户确认原灯效恢复正常，进程退出码 0。

这证明当前固件能执行主键区亮度升降及熄灭，不能据此声称现有 AirPulse 已完全兼容：生产 `apply_and_verify` 和 `automatic_matches` 仍严格比较未经缩放的原始 RGB。10% 与 60% 的回读会违反当前规则；0% 时 RGB 保留了前一步值，也不适合直接套用所有亮度统一乘法的规则。

本轮未校准绝对亮度，未验证其他颜色、新图形字段恢复或逐键自定义，也未修改生产代码。

## 后续混合色复测

运行现有 `--test-main-rgb`，使用生产共用 `apply_and_verify`，每步重新写颜色块再独立提交亮度。

紫色 `#A020F0`、青色 `#12B4C8`、白色 `#FFFFFF` 在 30% 亮度下，严格参数回读和人工观察全部通过；全黑熄灭、侧灯保护、原灯效恢复也全部通过，进程退出码 0。

这组结果修正了“低亮度回读总会缩放”的推断：相同固件下，30% 混合色可以保留原始 RGB。先前只写一次蓝色后连续修改亮度时的缩放仍是有效观察，但不能直接推广到所有生产写入路径。下一步应对照逐步重写颜色与单独连续改亮度的差异，不能仅放宽全部 RGB 校验。
